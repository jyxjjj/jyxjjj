# 注释与文档

## 内容与表达

- 注释、文档和变更说明优先描述当前代码做什么，不描述它没有做什么
  - 除非某个被避免的行为是需求约束、安全边界或此次改动的核心，否则不要写 '无需 X'、'不再 X'、'避免 X' 之类的否定式实现历史
  - 只描述这是什么菜，不要描述菜里没放什么
  - 永远不要出现`番茄炒蛋(无土豆版)`
- 注释和文档描述当前持续成立的行为、契约和约束，变更说明描述本次实际变化，均省略与本次需求无关的对照和补充背景
- 新增或扩写注释前，先判断它是否补充了代码、命名、类型或邻近说明尚未清楚表达的必要信息，仅有内容准确不足以成为新增理由
- 注释和文档中的业务规则、设计理由及安全、性能、兼容性说明，必须有代码、配置、测试或可靠资料支持，不推测或补造理由
- 注释和文档应让未参与当前对话的维护者独立理解，必要背景保存在项目中合适的位置

## 信息归属

- 注释的信息范围应与对应代码的职责范围一致，不把调用方或其他模块的业务细节写入本处注释
- 公共业务规则、接口契约和字段含义，在负责定义它们的位置集中维护，其他内部位置仅说明自身职责和必要的依赖关系，对外文档保留使用者理解契约所必需的信息
- 通用工具、转换层和生成器的注释应在具体业务内容变化时继续成立，仅在其自身职责、行为或约束变化时更新

## 修改与清理

- 日常修改代码时，仅更新因本次改动而失实的注释和文档，仍然准确的原文保持不变
- 不因措辞偏好、风格统一或补充本次改动背景，扩写、润色或复制其他位置的注释和文档
- 用户明确要求生成、清理或精简时，在指定范围内判断说明的必要性、准确性和归属，再决定新增、保留、缩短、合并或删除，不能仅因内容准确就保留重复说明
- 修改生成源前，确认改动属于本次需求，公共说明在源头维护，生成结果按项目现有流程同步
- 区分普通说明文字与具有工具、生成或法律意义的内容，保留必要的注解、指令、生成标记和许可证声明，修改前核实其作用
- 上述规则约束本次新增、直接受影响或用户明确指定清理的内容，不授权顺手清理其他既有说明、重构代码或调整生成流程，范围外问题仅报告
